2. ANÁLISE INICIAL DO PROJETO
--------------------------------------------------------------------------------
2.1. Arquitetura ROS 2 do robô:
  - BASE: controle diferencial via ODrive (CAN ou USB), publica wheel/odom
    e consome cmd_vel. Nós: odom_node, odom_node_copy, odom_node_usb.
  - SENSORES: câmera ZED2 (zed-ros2-wrapper) + RPLidar (sllidar_ros2),
    com TFs estáticas base_link → laser, base_link → zed_camera_link, etc.
  - LOCALIZAÇÃO: EKF (robot_localization) fundindo wheel/odom + zed/odom
    + zed/imu, AMCL (nav2_amcl) + map_server, e localization_manager
    (rotina de boot que tenta checkpoint e dispara movimentos de
    convergência: spin 360° + vai-e-volta).
  - NAVEGAÇÃO: Nav2 stack (controller_server com MPPIController,
    planner_server com SmacPlanner2D, bt_navigator, behavior_server) +
    mission_orchestrator (DSL JSON com Speak/GoTo/Tour/Wait/AwaitCommand/
    ReturnHome) + teleop_relay com watchdog.

2.2. Estado inicial dos pacotes "_teste" (já parcialmente trabalhados pelo
     usuário antes desta tarefa):
  - Já tinham `namespace` declarado nos launches, mas com hardcode "robot2".
  - Frames TF, tópicos absolutos (/cmd_vel, /plan, /ui/...), e chaves
    YAML como `robot2:` ainda apareciam hardcoded em vários arquivos.
  - localization.launch.py do _teste apontava para o pacote ORIGINAL
    (mjv_robot_fleet_localization), não para o _teste — bug latente.
  - mission_orchestrator com path absoluto antigo do missions.json
    (/home/mjv/ros2_ws/...).

2.3. Decisões arquiteturais aprovadas pelo usuário antes da implementação:
  (1) Nomenclatura: padrão numérico robot1, robot2, robot3, ...
      Default mantido em "robot2" para preservar fluxo atual.
  (2) Map server COMPARTILHADO entre robôs (1 instância, fora de namespace).
      AMCL fica dentro do namespace de cada robô.
  (3) Cenário de hardware: cada robô tem sua própria Jetson com seus
      próprios periféricos (CAN, USB do LiDAR). Defaults `can0` e
      `/dev/ttyUSB0` servem para todos.
  (4) Namespace é argumento overrideável, com default "robot2".
  (5) Compatibilidade legacy não é exigida — pacotes _teste sempre rodam
      com namespace.


3. ESTRATÉGIA DE ESCALABILIDADE
--------------------------------------------------------------------------------
3.1. Princípios aplicados:
  (a) Namespace por robô prefixa todos os nós, tópicos e actions.
  (b) TF prefix por robô: cada robô tem sua própria árvore TF
      (robotN/odom, robotN/base_link, robotN/laser, robotN/zed_camera_link,
      robotN/zed_imu_link). Apenas o frame "map" é global compartilhado.
  (c) Tópicos RELATIVOS no código Python (sem barra inicial) — assim o
      runtime do ROS 2 prefixa automaticamente com o namespace do nó.
  (d) YAMLs com chave wildcard `/**:` para aceitar qualquer nome de nó,
      independente do namespace em que ele rode.
  (e) Substituição de frames em runtime via PyYAML (decisão de não
      depender de nav2_common.launch.RewrittenYaml — ver seção 6).
  (f) Map server compartilhado, controlado por argumento `share_map`.

6. PROBLEMAS ENCONTRADOS E SOLUÇÕES APLICADAS
--------------------------------------------------------------------------------

6.1. Erro: Module 'nav2_common' não encontrado
  Sintoma:
    ModuleNotFoundError: No module named 'nav2_common'
    ao executar `ros2 launch mjv_robot_fleet_localization_teste
    localization.launch.py --show-args`.

  Causa:
    A versão inicial dos launches usava `from nav2_common.launch import
    RewrittenYaml` para reescrever YAMLs em runtime. O pacote
    ros-humble-nav2-common não está instalado nesta máquina (verificado
    com `apt list --installed | grep nav2-common` e `find /opt/ros/humble
    -name nav2_common`).

  Solução adotada:
    Refatorar os 3 launches (amcl_loc, localization, navigation) para
    usar PyYAML diretamente em vez de RewrittenYaml. Implementadas
    funções _materialize_*_yaml que:
      - Leem o YAML original.
      - Modificam in-memory as chaves de frame.
      - Gravam um arquivo temporário em /tmp.
      - Retornam o caminho do arquivo temp para ser usado pelo nó.
    Vantagens:
      - Sem dependência externa adicional.
      - Substituições mais previsíveis (apenas onde queremos).
      - Funciona em qualquer ambiente com ROS 2 + PyYAML (sempre presente).

6.2. Problema: RewrittenYaml aplicaria substituições em todos os lugares
  Antes da decisão de não usar RewrittenYaml, foi identificado um
  problema conceitual: a chave `global_frame` aparece em vários nós do
  Nav2 — em `bt_navigator` e `behavior_server` deve ser "map", mas em
  `local_costmap` deve ser "robotN/odom". RewrittenYaml sobrescreveria
  TODAS as ocorrências da chave com o mesmo valor.

  Solução adotada:
    - Para o local_costmap: usar placeholder "<NAMESPACE>/odom" no
      YAML, substituído por text replace antes do parse.
    - Para os demais (que devem permanecer "map"): deixar literal "map"
      no YAML.
    - Walk recursivo em PyYAML cuida de robot_base_frame (que SEMPRE
      vira <ns>/base_link) e do scan.topic.

6.3. Workspace de produção diferente do diretório de trabalho
  Identificado durante a fase de testes que:
    - PROJECT ROOT do contexto: /home/arthur/src/
    - Workspace ROS 2 efetivo do estágio: /home/arthur/MJV_robot2/
  Ambos contêm pacotes com o MESMO nome, mas com conteúdos divergentes
  (devido a histórico de cópias manuais).

  Resolução:
    - Todas as edições foram feitas em /home/arthur/src/ conforme o
      PROJECT ROOT informado.
    - Após validação completa (build + smoke test), os 4 pacotes
      foram COPIADOS para /home/arthur/MJV_robot2/src/, com backup
      automático dos pacotes antigos sob sufixo
      `.bak_20260512_relatorio` para permitir rollback se necessário.


7. ALERTAS IMPORTANTES PARA O USUÁRIO
--------------------------------------------------------------------------------

ALERTA 1: Mudança no contrato com a UI (mjv_ui_bridge / mjv-ui)
  Os tópicos do mission_orchestrator que antes eram absolutos:
      /ui/start_mission
      /mission_ctrl
      /ui/progress
      /tts/say
  agora são relativos e ficam dentro do namespace do robô. Para
  controlar o robot2, a UI precisa publicar/subscrever em:
      /robot2/ui/start_mission
      /robot2/mission_ctrl
      /robot2/ui/progress
      /robot2/tts/say
  AÇÃO NECESSÁRIA: ajustar a UI (mjv-ui ou mjv_ui_bridge) para
  contemplar o namespace do robô. Recomenda-se que a UI tenha um
  parâmetro/dropdown para selecionar com qual robô conversar.

ALERTA 2: Map server compartilhado — convenção de subida
  O argumento `share_map` controla se o map_server é instanciado.
  REGRA OPERACIONAL:
    - O PRIMEIRO robô a subir deve usar share_map:=true (default).
    - Os demais robôs devem usar share_map:=false.
  Se dois robôs subirem com share_map:=true ao mesmo tempo, haverá
  conflito de dois map_servers tentando publicar /map.

ALERTA 3: last_pose_path único entre robôs
  O argumento last_pose_path tem default /home/arthur/.mjv/last_pose.yaml,
  que NÃO inclui o namespace. Se múltiplos robôs rodarem na mesma
  Jetson (caso atípico), um sobrescreverá o checkpoint do outro.
  Recomendação no docstring do launch: cada robô passar
  `last_pose_path:=/home/arthur/.mjv/<ns>/last_pose.yaml`.
  Optou-se por NÃO automatizar essa concatenação para preservar
  controle explícito do usuário.

ALERTA 4: lifecycle_manager_navigation removido do nav2_params.yaml
  A seção lifecycle_manager_navigation com node_names hardcoded
  (robot2/controller_server, etc.) foi REMOVIDA do YAML. O
  nav2_bringup já cria seu próprio lifecycle manager dentro do
  namespace, portanto não é necessário.
  Se alguma rotina externa dependia da configuração antiga,
  precisará ser ajustada.

ALERTA 5: Pacotes "_teste" são incompatíveis com fluxo legacy
  Os pacotes _teste agora EXIGEM que o namespace seja informado
  (default "robot2"). Não é mais possível subir um nó sem
  namespace e esperar tópicos absolutos como /cmd_vel funcionando
  como antes. Esta foi uma decisão alinhada com o usuário.

ALERTA 6: Cache de pose / variáveis de ambiente
  O parâmetro `last_pose_path` aponta para um arquivo no home do
  usuário arthur. Se o serviço systemd (mjv_bringup.service ou
  mjv_nav2.service) rodar como outro usuário, esse path precisa ser
  ajustado.

ALERTA 7: Arquivos temporários em /tmp não são limpos
  Os launches geram arquivos temporários em /tmp/nav2_<ns>_*.yaml,
  /tmp/ekf_<ns>_*.yaml, /tmp/amcl_<ns>_*.yaml a cada subida do stack.
  Esses arquivos são úteis para debug, mas não são removidos
  automaticamente. Em uso prolongado, considere limpeza periódica
  (ex: tmpfiles.d ou cron).

ALERTA 8: Diretório de trabalho duplicado
  Existem dois workspaces no sistema com pacotes de mesmo nome:
    - /home/arthur/src/ (onde o desenvolvimento foi feito)
    - /home/arthur/MJV_robot2/ (workspace de produção)
  Após a tarefa, /home/arthur/MJV_robot2/src/ foi atualizado com a
  versão refatorada. Se houver builds antigos no install/ ou build/
  do MJV_robot2, recomenda-se rodar:
      cd /home/arthur/MJV_robot2 && rm -rf build install log
      colcon build --symlink-install
  Para garantir um build limpo.

ADENDO 2 — Frames TF da câmera ZED (12/Maio/2026)
================================================================================

A2.1. Problema relatado pelo usuário:

  Após a refatoração inicial, ao mudar o nome dos tópicos e frames no
  launch da câmera ZED, alguns frames internos da ZED (por exemplo
  camera_link_left, camera_link_right) ficavam "ocultos" ou inacessíveis
  na árvore TF. O usuário não conseguia referenciá-los no namespace
  pretendido.

A2.2. Diagnóstico:

  Análise do código fonte do zed-ros2-wrapper revelou que o pacote
  constrói TODOS os seus frames TF internos a partir de UM ÚNICO
  parâmetro: `camera_name`. Veja função setTFCoordFrameNames() em:
    zed_components/src/zed_camera/src/zed_camera_component_main.cpp:1985

    mCenterFrameId      = mCameraName + "_camera_center";
    mLeftCamFrameId     = mCameraName + "_left_camera_frame";
    mLeftCamOptFrameId  = mCameraName + "_left_camera_frame_optical";
    mRightCamFrameId    = mCameraName + "_right_camera_frame";
    mRightCamOptFrameId = mCameraName + "_right_camera_frame_optical";
    mImuFrameId         = mCameraName + "_imu_link";
    mBaroFrameId        = mCenterFrameId;
    mMagFrameId         = mImuFrameId;
    mDepthFrameId       = mLeftCamFrameId;
    mPointCloudFrameId  = mDepthFrameId;
    ...

  Pontos críticos:
  (a) Frames TF são strings GLOBAIS no ROS 2 — diferente de tópicos,
      eles NÃO recebem prefixo automático do namespace ROS 2.
  (b) Com camera_name="zed2" hardcoded (default no launch antigo),
      múltiplos robôs publicariam frames com nomes IDÊNTICOS, causando
      colisão silenciosa na árvore TF (último a publicar vence).
  (c) Os TFs estáticos artificiais que existiam no launch
      (`zed_camera_link`, `zed_imu_link`) não correspondiam aos nomes
      reais publicados pelo ZED, criando frames ÓRFÃOS na árvore.

A2.3. Solução adotada:

  (a) Tornar `camera_name` DINÂMICO com base no namespace e modelo:
        camera_name_str = [namespace, "_", camera_model]
      Para namespace="robot2" e camera_model="zed2", o ZED passa a
      publicar frames com prefixo único:
        robot2_zed2_camera_center
        robot2_zed2_left_camera_frame
        robot2_zed2_left_camera_frame_optical
        robot2_zed2_right_camera_frame
        robot2_zed2_right_camera_frame_optical
        robot2_zed2_imu_link

  (b) Ajustar o TF estático que conecta o robô à câmera para apontar
      para o frame raiz REAL publicado pelo ZED:
        TF: <ns>/base_link -> <ns>_<modelo>_camera_center
      A partir desse frame raiz, o próprio nó ZED publica TFs internas
      (camera_center -> left, right, imu) com calibração correta.

  (c) Ativar `publish_imu_tf=true` (estava false) para que o ZED
      publique sozinho a TF camera_center -> imu_link com calibração
      interna, em vez de mantermos um TF estático artificial.

  (d) REMOVER os TFs estáticos artificiais zed_camera_link e
      zed_imu_link, que eram offsets zero e desconectados dos frames
      reais da ZED.

A2.4. Árvore TF resultante (exemplo robot2):

  map  (compartilhado entre robôs)
   └─ robot2/odom  (publicado pelo EKF/AMCL)
       └─ robot2/base_link  (publicado pelo EKF)
           ├─ robot2/laser  (TF estático, sensors.launch.py)
           └─ robot2_zed2_camera_center  (TF estático, sensors.launch.py)
               ├─ robot2_zed2_left_camera_frame  (publicado pelo ZED)
               │   └─ robot2_zed2_left_camera_frame_optical  (ZED)
               ├─ robot2_zed2_right_camera_frame  (publicado pelo ZED)
               │   └─ robot2_zed2_right_camera_frame_optical  (ZED)
               └─ robot2_zed2_imu_link  (publicado pelo ZED)

  Para um segundo robô (robot1), a estrutura é simétrica e independente,
  com prefixo "robot1" — sem colisão de frames.

A2.5. Trade-off / convenção mista:

  Frames do robô usam BARRA: robot2/base_link, robot2/odom, robot2/laser
  Frames da ZED usam UNDERSCORE: robot2_zed2_left_camera_frame, etc.

  Isso é uma limitação imposta pelo wrapper da ZED (caixa preta), que
  não aceita prefixo de namespace ROS 2 nem permite caracteres especiais
  como "/" no camera_name. Para forçar barras, seria necessário
  recompilar o wrapper modificando setTFCoordFrameNames(), o que está
  fora do escopo desta tarefa e quebraria a manutenibilidade.

  Impacto prático: nós DOWNSTREAM que referenciam frames da ZED (RViz,
  processamento de imagem, etc.) precisam usar EXATAMENTE os novos
  nomes. Por exemplo, em RViz, ao adicionar uma exibição de Image,
  selecionar topic /robot2/zed/left/image_rect_color (com namespace) e
  o frame de referência correspondente robot2_zed2_left_camera_frame.

A2.6. Erro encontrado durante implementação:

  Tentativa inicial:
    zed_root_frame = [camera_name_str, "_camera_center"]
  onde camera_name_str = [namespace, "_", camera_model]

  Resultado: erro do launch — "list within list" não é aceito pela
  função normalize_to_list_of_substitutions do ROS 2 launch system.

  Correção: achatar manualmente em uma única lista de substitutions:
    zed_root_frame = [namespace, "_", camera_model, "_camera_center"]
